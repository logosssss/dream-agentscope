AgentScope 落地实战 02｜概念地图

五个对象、30 个装配点与一次懒启动 · 阅读约 14 分钟

仓库没有 demo 模块。能独立跑通的最小闭环在 agent-bootstrap 的测试目录：AccessChannelBootstrapAgentTest，97 行，其中不到 20 行是一个返回固定文本的 Model 桩。没有 Spring 容器，没有数据库，从装配走到回复。

GatewayBootstrap.builder()
  .configureAllAgents(builder -> {
    builder.model(model);
    builder.disableWebTools();
  })
  .agent("companion-v1", builder ->
      builder.agentId("companion-v1")
             .sysPrompt("companion"))
  .mainAgent("companion-v1")
  .channel(ChatUiChannel.create())
  .build()
  .start();

这段代码里的每个类型，在正式链路里都对应一个位置。把边界记住比记 API 名字有用：出错时先判断问题落在哪个对象上，再去看那一层。

这篇要回答三个问题

1. 五个对象各自的边界，一条消息在它们之间怎么走。

2. 装配期、启动期、请求期分别发生什么，哪一步在请求路径上。

3. 哪些约束违反之后不报错，只在并发或热更时表现成别的问题。

一、五个对象

对象 职责 正式链路位置
GatewayBootstrap 装配入口，一次建好所有 Agent 与 Channel startGatewayLocked
Builder 可变的装配器，每个 Agent 一个 HarnessAgentFactory
Channel 收发消息的通道，不是 HTTP 控制器 ChatUi / Api
Msg 一轮消息；回复与审批确认都靠它 execute / resumeConfirm
RuntimeContext 一次调用的上下文，跨中间件传递 AgentTurnSupport

Channel 容易被当成 Controller 用。它不处理 HTTP，也不做鉴权，只负责把一条用户消息交给 Gateway 并把事件流吐回来；鉴权与额度在 agent-access 里已经做完，进到 Channel 的只有 userId、sessionId 和文本。

Msg 的另一个用途是审批续跑。用户在页面上点"允许"之后，回到 Gateway 的不是一段新对话，而是一个带 METADATA_CONFIRM_RESULTS 元数据的 Msg，resumeConfirm 把它交给同一个 Agent 续跑。所以"点确认"和"发消息"在框架层是同一件事。

二、一条消息在五个对象之间怎么走

把五个对象连起来看，一次对话分三段：接入层、Gateway、Channel。接入层在 ChatAppService，同步与流式用的是同一串门禁，顺序固定：

① 拒绝显式 channel=API

WEB 入口只接默认通道，程序调用走 ApiAgentChatController。

② 转 AgentRequest

身份只取登录会话写进线程的值，请求体里的 userId 丢掉。

③ 四道门禁

requireUser → 租户 → 租户用户 → 会话归属。

④ 额度

quota.check 记请求次数，读已用的 token 与费用。

⑤ 并发名额

concurrent.open 占一个租户名额，流式到结束时才放。

⑥ 落会话，再执行

remember 写会话索引，之后才 executor.execute。

顺序不是随手排的。租户与归属校验在额度之前，无效请求不会消耗额度计数；额度在并发占位之前，被额度拒绝的请求不占名额；会话落库在占位之后，记失败就释放名额并让这一轮失败，不会留下"有名额没记录"的状态。

进到 ChannelGateway 之后只剩四件事：turns.require 校验请求、drain.beginTurn 记一次在途、turns.context 建本地上下文、options() 拼好 SendOptions 交给 channel().send。同步、流式、API 通道三条路是同构的，差别只在最后调 send 还是 sendStream。

options() 里有一处容易看漏：会话用请求里的 sessionId，调用方只暂存 tenantId 与 agentId；agentId 为空或等于 mainAgentId 时不改路由，仍走 Bootstrap 的 main Agent。

通道名不进 AgentRequest。channel 只在接入层用于会话列表展示与入口选择，运行层拿不到它，也不需要知道这条消息是从网页还是从程序调用进来的。

回程同理：Channel 吐 AgentEvent，经 turns.mapStreamEvent 变成 AgentStreamEvent，最后由 Controller 包成 ServerSentEvent。HTTP、SSE、鉴权都在最外两层，五个对象里没有一个知道它们存在。

三、公共项对每个 Agent 各跑一次

configureAllAgents 看起来像"全局配置，执行一次"，实际不是。测试里有三个计数器：

assertThat(commonHits.get()).isEqualTo(2);
assertThat(companionHits.get()).isEqualTo(1);
assertThat(echoHits.get()).isEqualTo(1);

两个 Agent，公共回调跑了两次。框架的顺序是：对每个 agent(id, consumer)，先跑公共回调，再跑该 Agent 的 consumer，consumer 返回后立即 build。

整段装配分三个期间、六步，只有最后一步在请求路径上：

装配期 · 每个 Agent 三步　公共回调 → 该 Agent 的 consumer → build()

启动期 · 两步　start() 建 Channel；从 agents() 取实例挂工具

请求期 · 一步　channel().send(...)

公共回调里不能放"只执行一次"的动作：累加计数、注册全局监听、开连接池，都会按 Agent 数量重复。

差异项拿到的 Builder 已经带着公共项，只能覆盖不能撤销。公共项关掉的 web、shell、动态 skill、动态子代理，在差异项里都没有对应的开启调用。

build 在 consumer 返回后立即发生，consumer 里不能把 Builder 存起来异步使用。

HarnessAgentFactory 的类注释把这条写成了一句硬约束：不要在线程之间共享同一个 Builder 再改提示词。

两组装配合起来是 30 处 Builder 调用：公共项 12 处，搭子差异 18 处。公共项决定这个进程不允许做什么，差异项决定这个 Agent 是谁。

四、工厂只持有"消费者"

工厂是单例 @Component，字段里没有任何 Builder：只有配置、模型解析器、中间件、工具列表。这些部件要么无状态，要么由 Spring 保证单例安全，所以工厂可以单例。

单例能成立的前提是"每轮状态都不在 Bean 里"。中间件是 Spring 单例，但 tracing、shutdown、audit 这些中间件不持有会话状态，判定结果写进 RuntimeContext，随调用走。工厂负责的是"怎么装"，不是"装完放在哪"。

反例是把 Builder 放进字段：

// 错误示范，不是仓库代码
private final HarnessAgent.Builder builder;

public void build(String prompt) {
    builder.sysPrompt(prompt); // 并发覆盖
    builder.build();
}

这个错误难查，不是编译期能发现，而是 setter 不报错、覆盖发生在并发窗口内，表现为"回复里出现另一个用户的设定"。正式链路里每个 Agent 只有一个 consumer，Builder 由框架在 build 前创建，用完即弃。

同一种错误模式也出现在懒启动入口：channel() 用双检锁，两个并发首请求只有一个会走 startGatewayLocked()。去掉双检锁不会立刻报错，但冷启动时并发的两个请求会各自建一套 Agent，后写入的那套覆盖前一套，前一套没人 close，模型连接与工具资源留在进程里。

五、长驻实例，懒启动

一个常见误解是"每次对话 new 一个 Agent"。当前实现不是：channel() 用双检锁拿 Channel，bootstrap == null 时才建 Agent。构造器注释写得明确：只接线，不立刻建模型；缺 DASHSCOPE_API_KEY 时仍允许进程起来。

① 未启动　bootstrap == null

↓ 首次对话 channel()

② 运行中　companion + echo 长驻

↓ 配置热更 rebuildAll()

③ 排空中　draining = true，新请求等待

↓ 在途归零或超时

④ 运行中　旧实例 close 后重建

时点 发生什么 代价
进程启动 只装配 Bean，不建 Agent 故障推迟到首次对话
首次对话 建两个 Agent，挂中间件与工具 首请求先装配再出字
配置热更 排空在途 → 停旧 → 建新 期间新请求阻塞
进程退出 同一把排水闸 最长等 120 秒

排水闸是 ResidentAgentDrain：draining = true 后，新请求在锁上循环等待；在途归零或超时后执行动作。超时不抛错，只记一条 warning 后继续重建，所以在途对话可能被新实例的 close 打断——这是"热更优先于长尾请求"的取舍。

重建还有一处连带影响：停旧时会清空待确认记录，热更窗口内没处理的审批不会跨实例保留，需要客户端重新发起。停机走的是同一把闸，但多一层框架侧配置——GracefulShutdownConfig(timeout, PartialReasoningPolicy.SAVE)，不再接新调用，已生成的推理内容保留；注册动作放在 ApplicationRunner 里，避免停机顺序抢在 Web 容器前面。

六、Toolkit 在 build 之后才存在

配置 Agent 时挂不了业务工具，因为那时 Toolkit 还没创建。工具只能在 start() 之后、取到实例再挂：

HarnessAgent companion =
    started.agents().get(mainAgentId);
agents.attachCompanionTools(companion);

CatalogToolRegistrar 做白名单过滤：目录里的 toolId 集合决定哪些实现被注册，同一标识只注册第一次，目录为空直接返回、不改 Toolkit。所以"加一个工具"不是改代码就行，还要在工具目录里登记，否则实现类存在也不会出现在模型的工具列表里。

"只注册第一次"这条和装配顺序绑在一起：同一 toolId 出现两个实现时，谁先注册谁生效，后一个被跳过，既不报错也不打日志。注册器注释还留了一句：传入的 Toolkit 应是这次 Agent 自己的，不要改共享实例。

工具集合的变更同样要靠重建生效，不能在运行中往 Toolkit 里加。

七、RuntimeContext 写三次

上下文不是构造一次传到底，而是三层依次合并：

① 调用方暂存

只放 tenantId 与 agentId；身份字段走 SendOptions。

② resolver 补键

以 caller 为基座补 tenantId；agentId 可从 MsgContext.extra 兜底。

③ Gateway 覆盖身份

进入 Agent 前写入 userId 与 sessionId，以登录态为准。

第三层的方向是单向的：调用方写不进去，只能被覆盖。所以"前端传一个 userId 冒充别人"在上下文这一层不成立，能改身份的只有登录态。

有一条约束写在 resolver 注释里：业务键不要塞进 MsgContext.extra()，那会进会话闸键。会话闸按 key 做同会话串行，把租户之类的字段塞进去，会让同一会话的两个请求落进不同键。

读取侧有两种写法：context.get("tenantId") 取字符串，context.get(RiskLevel.class) 取类型化对象。后者是中间件之间传递判定结果的通道：安全门写入 RiskLevel.CRITICAL，压缩与记忆中间件读它来决定是否跳过。

用类型当键的好处是不会和字符串键撞名，代价是同一类型只能承载一个值：两处中间件都写 RiskLevel 时，留下的是后写的那个，顺序变成了语义的一部分。

八、30 个装配点分两组

30 处 Builder 调用里，公共项 12 处，按作用分五组：

分组 调用 作用
能力开关 disableWebTools / disableShellTool 未做出口白名单前关掉内置 web 与 shell
记忆 memory / disableMemoryHooks 开跨会话记忆，关框架自带 flush hook
上下文治理 disableCompaction / disableToolResultEviction / disableDynamicSkills / disableDynamicSubagents 四个动态能力显式关闭，改由产品中间件接管
权限与追踪 permissionContext / middleware(tracing) 无条件规则 + OTel 追踪中间件
停机与状态 middleware(shutdown) / distributedStore 优雅停机闸；有 Store 才挂

搭子差异 18 处，按作用分四组：

分组 调用
身份 name / agentId / model / sysPrompt / maxIters / workspace
子代理与 MCP subagent / toolsConfig / mcpServerRegistrationListener
文件系统 filesystem（Sandbox 开则 Docker，否则 Remote）
中间件 audit / fileWriteLimit / approval / safetyGate / eviction / compaction / persona / memoryFlush

中间件的实际顺序由装配顺序决定，没有显式排序：公共项先跑，所以 tracing、shutdown 在链首；搭子再按调用顺序追加 audit → fileWriteLimit → approval → safetyGate → eviction → compaction → persona → memoryFlush。

这个顺序有语义，不能随手调。

safetyGate 之前不能截断内容，否则危机判定拿不到原文；eviction 必须在 compaction 之前，先截大工具结果再压历史；memoryFlush 放最后，靠本轮已确定的 RiskLevel 决定是否入队。

maxIters 也不取单一来源：先读运行配置，配成小于 1 时退回产品域的 completion.maxIterations()，仍无效时按 20。测试里显式设成 1，是为了让桩模型一轮就结束。

九、事件出口不暴露框架类型

流式接口吐的是框架的 AgentEvent，接入层拿到的是 AgentStreamEvent(type, text)：

String type = event.getType()
        .name().toLowerCase();
return new AgentStreamEvent(
        type, textOf(event));

text 按事件种类取短文本，四类分支：

增量事件

取 getDelta()，就是前端逐字显示的那段。

工具开始

取工具名，前端据此显示"正在调用"。

审批事件

取逗号拼接的工具名，不带参数。

结束事件

取全文，并过一遍出站检查 ModelTextGuard.outbound。

工具参数与完整提示词不放进 text。理由是这一层同时给前端和日志用，参数里可能带用户原文，一旦进 SSE 就等于把出站检查绕过去了。这层的价值是隔离：框架换事件类，只改映射，SSE 格式不动。

十、五条约束汇总

约束 违反后的现象
公共项按 Agent 数量重复执行 计数翻倍、监听重复注册
Builder 不可跨线程共享 提示词互相覆盖，回复串人设
Agent 长驻，热更靠重建 改配置不生效，或工具丢失
Toolkit 只能在 build 之后挂 工具注册为空，模型看不到工具
业务键不进 MsgContext.extra 同会话串行失效

五条里有四条不会在启动时报错，只会在并发、热更、或某次审批续跑时表现成"看起来像模型的问题"。判断顺序建议按对象来：先看请求进没进 Gateway，再看 Channel 有没有被懒启动起来，最后看 Agent 里挂的工具与中间件是不是这一版。
