## 六处假设

把 Agent 接入既有 Java 后端系统时，最先失效的不是模型能力，而是六处来自 Web 框架的默认假设。以下按假设逐条给出失效机制与仓库中的替代实现，涉及的行为均可在代码与各模块 README 中核对。

## 假设一：接口同步返回

Spring MVC 的默认形态是请求进入、处理完成、返回响应体。按此形态封装的 Agent 调用如下：

```java
// 同步封装
public AgentResponse chat(String text) {
    return agent.call(text, context);   // 阻塞至模型生成结束
}
```

该实现可以运行，但存在三个不可回避的问题：

- **延迟不可控**：整段生成完成才返回，长回答耗时可达数十秒，网关与浏览器先超时。
- **进度不可见**：生成过程中无任何中间状态，前端只能显示 loading。
- **取消无法传递**：客户端断开后，服务端仍在生成并计费。

Agent 的原生形态是事件流，不是返回值：

```java
agent.streamEvents(userText, context)
     .doOnNext(event -> sse.send(event))    // 增量下发
     .doFinally(sig -> agent.close());      // 完成、取消、异常统一关闭
```

改造后需同步调整三处语义：

| 项 | 同步模型 | 流式模型 |
|---|---|---|
| 超时含义 | 全段耗时的上限 | 全段耗时的上限，首字延迟另有指标 |
| 失败表达 | HTTP 状态码 | 流建立后状态码恒为 200，失败在事件中表达 |
| 资源释放 | 返回值即结束 | 取消与异常路径都必须执行 close |

其中第三项是主要泄漏来源：`Flux` 被取消时不会走 `onComplete`，只走 `doFinally`。资源释放逻辑写在前者里，客户端一关页面就漏。

## 假设二：事务可回滚

数据库操作的思维定式是：异常回滚，最坏情况脏一条记录。Agent 调用不具备这个性质——token 已消耗、费用已产生、工具可能已对外产生副作用，均不可逆。

替代方案不是补偿事务，而是**事前占位、事后收敛**：

```java
// 1. 幂等：同一 X-Request-Id 十分钟内重复提交直接拒绝
// 2. 占位：turn:{tenant}:{user}:{session}，同会话不允许并行两轮
// 3. 校验通过才进入模型
if (!quotaGuard.tryAcquire(...)) throw new BusinessException(CONFLICT);
try {
    return executor.stream(request);
} finally {
    quotaGuard.release(...);   // 尽力释放，不补偿已发生的消耗
}
```

两个与直觉相反的设计点：

**Redis 不可用时返回 503，不降级。** 额度、限流、幂等、占位四条路径全部依赖 Redis。降级到进程内存后，多实例各自计数，额度上限失效；降级到 MySQL 后，单次对话增加十余次查询，慢查询进入主链路。两种降级的实际风险都高于直接拒绝服务。

**释放失败不回滚已有结果。** 占位键由 TTL 兜底过期，释放属于尽力而为。此处的一致性目标是最终一致，而非强一致。

## 假设三：一次调用对应一次返回

服务间调用是一问一答。Agent 的工具调用是循环：模型推理、决定调用工具、读取结果、继续推理，循环次数由模型决定。项目配置的 `max-iters` 默认值为 20，该值不是性能参数，而是**单次对话的成本上限**——每轮循环都是一次完整的模型调用。

由此产生三项必须提前设计的约束：

| 约束 | 原因 | 项目中的取值 |
|---|---|---|
| 超时按整段计算 | N 轮循环累加 | `timeout-seconds` 默认 120 |
| 工具必须幂等 | 模型可能以相同参数重复调用 | 工具实现侧保证 |
| 副作用设硬上限 | 单轮可能写入超大内容 | `max-write-bytes` 默认 5MB，超出丢弃 |

另有一类行为需要提前接受：**模型可能一次都不调用工具**。检索工具是否被使用由模型判断，这是 Agentic 模式的正常行为。工具提供的是能力，不是流程；需要固定流程时应使用工作流而非 Agent。

## 假设四：输出确定，可逐段校验

内容安全的常规做法是请求进入时校验、通过则放行。将该做法平移到流式输出——对每个增量做敏感词匹配、命中即中断——会产生两类错误：

- **误判**：危险词的判定依赖完整句式，片段匹配会命中正常表达的局部。例如输入"了解自杀干预的法律责任"，增量在"自杀"处即触发。
- **漏判**：真正违规的整句被拆成多个增量，任一片段都不命中。

原因是流式增量不构成语义单元。可行做法是**缓冲后校验**：

> 增量先暂存不下发，整段生成结束后对完整文本执行规则校验；命中则整段替换为预设回复。

代价是首字延迟上升，属于合规与体验之间的直接取舍。项目还做了分级：危机档校验输出文本，升高档只追加克制标记、不中断输出——后者误判率更高，中断正常回答的代价大于放过边缘内容。

## 假设五：权限是静态注解

`@PreAuthorize` 一类声明的权限在编译期固定。Agent 的工具权限是运行时决策，且有三态：

| 状态 | 行为 | 决策来源 |
|---|---|---|
| `ALLOW` | 直接执行 | 配置中心 / 权限表 |
| `ASK` | 挂起，等待用户确认 | 运行时中间件 |
| `DENY` | 从本次调用的工具集中移除 | 同上 |

实现时容易走错的一步是给框架临时追加权限规则。AgentScope 的默认权限上下文为 trivial，动态追加规则有两种结果：本次判定读取不到该规则；或使同一次调用中未匹配到的工具一并变为"询问"。因此执行策略应挂在中间件上，而非修改权限引擎。

另一处需要写入产品文档的语义：**审批通过不等于工具执行**。审批只解除拦截，用户需重新发送上一条消息，下一轮循环才会真正调用工具。原因是 Agent 的一轮是"模型决策 + 工具执行"的原子循环，中途插入一次工具执行会产生半个轮次，上下文无法对齐。

## 假设六：Bean 单例复用

Spring 的默认约定是单例、无状态、共享。Agent 的 Builder 是可变的：若注册为单例 Bean，并发请求会互相覆盖提示词，造成身份与提示词错配。

项目容器中不存在 `HarnessAgent` 类型的 Bean，构建发生在请求内：

```java
var agent = factory.newBuilder(request).build();
try {
    return agent.call(text, context);
} finally {
    agent.close();
}
```

每次请求新建、结束关闭，以对象创建开销换取并发正确性。随之产生的约束是 Agent 不持有跨请求状态，会话、轮次、记忆必须显式持久化——这也是该结构能够水平扩容的前提。

## 替代规则汇总

| 原假设 | 替代做法 | 关键约束 |
|---|---|---|
| 同步返回 | 事件流为一等公民 | 取消路径必须释放资源 |
| 事务回滚 | 幂等键 + 占位锁 | 失败只释放占位，不补偿消耗 |
| 单次调用 | 按循环设计 | 超时、幂等、副作用上限 |
| 输出确定 | 缓冲后整段校验 | 接受首字延迟上升 |
| 静态鉴权 | 运行时三态决策 | 不改权限引擎，挂中间件 |
| 单例复用 | 每请求构建 | 状态显式持久化 |
